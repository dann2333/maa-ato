# 调研结论摘要

四轮并行调研（MAA 生态与游戏数据 / 自我进化与多模型互学 / 数据获取与感知 /
外围模块对抗审查）的**可执行结论**，只保留会改变决策的部分与其数字。

> 凡未在本仓库独立验证的，标注「未验证」。不要把它们当既定事实去写代码。

---

## 1. 模拟器可行性：部分可行

**数据完全覆盖**：地图几何、敌人路线与检查点、刷怪调度、经济与胜负条件、
难度 rune、干员/敌人属性、攻击范围。这部分可以做到位精确。

**数据完全不覆盖**（必须手写 + 实机标定）：

| 缺口 | 量级 | 后果 |
|---|---|---|
| 技能/天赋/敌人特性的**行为语义** | `skill_table` blackboard 有 1,020 个不同键，**732 个只出现一次**；敌人技能 715 个 prefabKey；talent blackboard 2,729 键 | 数据里只有参数袋，行为在编译后的客户端里。这是保真度的硬上限 |
| 伤害公式 | `gamedata_const` 只有 UI 归一化上限 | 物理/法术公式与 5% 保底全部来自社区逆向，必须实机验证 |
| 动画帧（抬手/后摇/是否重置攻击计时） | 唯一公开来源已停更（2021），对 1,810 技能覆盖率 < 15% | 见 SIM_SPEC E-6 |
| RNG | 刷怪组成、闪避、概率天赋均随机 | **推论：按分布规划，不要按固定轨迹规划** |

## 2. 数据源排序（价值/成本）

| 级 | 源 | 关键数字 |
|---|---|---|
| S1 | 公开 gamedata JSON | ~350 MB，数分钟。没有它下面每一步都没有标签空间 |
| S2 | MAA 作业语料 | **40,854 份 / ~282,000 条专家动作 / ~53 MB**，零感知成本，等价约 2,000 小时视频 |
| S3 | 解包 4 个战斗逻辑 bundle | **仅 5.2 MB**，含 2,677 条弹道速度 + 922 个技能时序字段，公开 JSON 里完全没有 |
| S4 | `bakemuzzledata`（已是公开 JSON） | 7,064 条 `OnAttack` 命中帧 |
| S5 | 自录对局 + 战斗日志 | 唯一 exact ground truth，用作校准 oracle 与回归金标 |
| A1 | B 站视频 | 买的是**分布广度**（失误、恢复、长尾关卡），不是标签数量。预算 200–400 小时 |

**四个陷阱**（明确不做）：训练 VPT 式 learned IDM（动作密度比 Minecraft 稀疏约 500 倍，
且每个动作都有设计好的持久 UI 痕迹，确定性检测器够用）；逐帧 OCR；21 GB 全量解包
（`hot_update_list` 里 gamedata/excel/levels 命中数为 0，全解包也拿不到模拟器要的东西）；
用 Auto Deploy 做噪声地板。

## 3. 作业语料的结构性缺陷（决定了它不能单独用）

语料是 **expert-but-degenerate**：全部预先规划、确定性、全部成功、大量
"此后全自动放技能"。**零失误、零恢复、零反应式重规划。**
只训它会得到一个遇到意外状态就崩的策略——这正是 VPT 用大量杂乱网络视频要防的东西。
→ 作业是**行为先验**，B 站视频补的是**分布广度**，两者不可互相替代。

回放还依赖精英化/等级/专精/模组/潜能档位。模拟器若不建模这些，回放会静默发散，
而发散的轨迹会被错标成「专家」。**任何未通关的回放必须丢弃。**

## 4. 自我进化：能做什么、不能做什么

**砍掉**：联赛式自博弈（明日方舟是 PvE，**不存在需要被击败的对手策略**；
最便宜的公开联赛实现需 144×V100 + 13,440 CPU 核 × 57 天）、POET、PAIRED。

**保留**：专家迭代结构（搜索当教师 → 蒸馏进反射策略）。但 ExIt 是在双人零和游戏上
验证的，那里对手本身就是难度阶梯；PvE 里一关打通后信号就变成常数。两个替代品：
- **Ranked Reward**：把回报对自己最近 N 场的分位数做阈值，门槛自动上移
- **游戏自带的难度轴**：rune 系统正是官方实现突袭的方式

**门禁便宜、训练昂贵**（完整配对门禁 88–177 秒）→ **门禁每代必跑，不许抽样**。

**特权落差在模拟器内部不存在**——sim 里的 agent 本来就能读全状态。
不对称只在 **sim→实机**边界上。修正了 I-3 的表述方式：
先在全状态上训战术（便宜），再蒸馏进只读像素的学生。

**搜索形态**：定时部署脚本上的 CEM，不是 tick 级 MCTS——干员上限 8–13 意味着
真正的决策点只有 30–80 个，MCTS 99% 的预算会浪费在无操作 tick 上。

## 5. 屏幕 ↔ 格子投影

摄像机 `view` 参数**不在 ArknightsGameData 里**，在 `Arknights-Bot-Resource/levels.json`
（4,186 关，168 个不同相机）。**不能从地图尺寸推出**：146 个不同 (宽,高) 组合里
有 55 个对应多于一个相机。

有完整参考实现与可回归的数值基准（半 FOV 20°、near 0.3、俯仰 30°、
tile z = `heightType × -0.4`）。16:9 下无需额外适配。

**注意**：另一个镜像把 `heightType` 存成整数 `1`，而投影公式要拿它做乘法。
本仓库已在 `ato.sim.grid._enum` 处理，见 CLAUDE.md §3。

## 6. 战斗回放日志（对「从游戏中学习」最相关的发现，未验证）

服务端保存每关的战斗日志，含**精确动作序列**（时间戳、干员、操作类型、朝向、行列）
与结算元数据（用时、结果、剩余费用/生命、击杀/漏怪数、随机种子、编队练度）。

**这是 sim-vs-real 校准的 exact oracle**，比视频强得多。但有三个硬限制：
每关**只有一个槽位**且覆盖写；需要该关无助战三星通关；且获取它需要非官方 API 客户端，
**存在账号风险**。现实产出约 1e4 条动作，是校准金标而非训练主力。

坐标是第三套约定（(1,1) = 左下，笛卡尔），接入时必须显式转换。

**这条需要用户拍板是否接受账号风险。**
